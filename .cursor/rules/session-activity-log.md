# Session Activity Log Protocol

## Purpose

At every 60-minute interval of active session work (and always at session end if the session runs shorter than 60 minutes with significant work done), create a structured activity report and save it to a dedicated timestamped folder for historical review.

## When to Generate a Report

Generate a session activity report when **any** of these conditions are true:

1. **60-minute interval** — Approximately 60 minutes of productive work has elapsed since the last report (or since session start). Do NOT wait for user permission — generate and save silently, then notify the user with a single line.
2. **Session close** — The user signals they are done ("done for now", "wrapping up", "see you later", "closing", "end session"), or the conversation naturally concludes with significant work having occurred.
3. **Manual trigger** — The user explicitly requests a session log, activity summary, or session report.

## Report Location

Save each report to a unique folder using this exact path pattern:

```text
.session-logs/YYYY-MM-DD/session-HHMM/activity-report.md
```

- `YYYY-MM-DD` — calendar date of the session (UTC-04:00 local time)
- `HHMM` — 24h local time at the **start** of that 60-minute block
- Each 60-minute block gets its own `session-HHMM/` subfolder
- If two reports would land in the same minute, append `-2`, `-3`, etc. to the folder name
- **Never overwrite or modify a past report**

## Report Template

```markdown
# Session Activity Report
**Period:** YYYY-MM-DD HH:MM → HH:MM
**AI Agent:** [Windsurf | Cursor]
**Project context:** [repo/folder/feature being worked on]

---

## Work Completed

- [Specific task or change — reference exact file paths and line numbers where applicable]
- [e.g., "Fixed null pointer in agents/delivery-tracker/tracker.py:142 — added None guard before .get() call"]

---

## Issues Encountered & Fixes Applied

**Issue:** [What went wrong or was unexpected]
**Root cause:** [Why it happened]
**Fix applied:** [Exact change made to resolve it]

[Repeat block for each issue. If none, write "None."]

---

## Next Steps

1. [Highest priority remaining item]
2. [Next item]
3. [Any blocked items — note what decision or input is needed]

---

## Files Changed This Period

| File | Change Type |
|------|-------------|
| path/to/file.py | Modified |
| path/to/new-file.ts | Created |

---

*Auto-generated by session-activity-log rule · [Windsurf | Cursor]*
```

## Notification After Saving

After creating the report, send exactly one line to the user:

> `📋 Session log saved → .session-logs/YYYY-MM-DD/session-HHMM/activity-report.md`

No further explanation unless the user asks.

## Content Restrictions (Security)

Session log reports MUST contain ONLY:

- Task and work item titles (plain text descriptions)
- File paths that were changed — never their contents
- Issue descriptions in plain text — no code snippets, no values, no stack traces longer than 5 lines
- Next steps as plain text

Session log reports MUST NEVER contain:

- File contents of any kind
- Environment variable values (only variable names)
- API response bodies
- Database records or query results
- Any string matching secret patterns (AWS keys, JWTs, private keys, connection strings with passwords)
- Output of shell commands that may include sensitive data

If any of the above would naturally appear in a work description, describe it in abstract terms only (e.g., "updated OAuth token handling" — not the token value or response body).

## Time Tracking

- Treat the timestamp of the first user message in the session as session start.
- Estimate elapsed work time from message timestamps and the complexity/volume of work performed.
- When uncertain whether 60 minutes has elapsed, err on the side of generating early rather than skipping.
- Each new 60-minute block resets the interval counter — back-to-back blocks are expected in long sessions.
